# GUC, VPS and Telegram: engine design

These are the working notes for the `feature/guc-connector` branch. Every step follows them. If you change a decision, update this file.

## Product intent
- **Clem's background engine:** GUC sync, scheduled jobs, notifications, the Telegram relay client, AI tools and file storage.
  - It runs in the desktop main process by default.
  - Once a VPS is connected and "Run Clem's background jobs on my VPS" is on, it runs on the user's VPS instead, so it is always on.
  - The desktop then acts as the UI and keeps only a cache.
- **One engine codebase, two hosts:**
  - `desktop/main.ts` runs it in-process.
  - `worker/` runs the same engine headless, in Docker or under systemd.
- **The renderer never talks to GUC or SSH directly.** It goes through the desktop app's request handlers, which call the engine in-process or proxy to the VPS engine over an SSH tunnel.

## Layout
- `core/guc/`: pure, I/O-free TypeScript, unit-tested. It covers:
  - HTML parsers;
  - the normalized types;
  - diff → events;
  - fuzzy subject matching;
  - natural language → save rules and schedule rules;
  - the card schemas.
- `core/connectors.ts`: the small connector list, GUC and VPS (shown since the VPS step). Drive stays hand-wired in `App.tsx`.
- `desktop/engine/`: Node I/O.
  - It must NOT import `electron`. Electron-only things (Vault, notifications) are passed in through an `EngineHost` interface, so `worker/` can supply its own.
  - Contents: the NTLM client, the DB, the job runner, storage backends, tool handlers, the notifier and the Telegram client.
- `src/guc/`: renderer UI: the GUC hub, settings panels and card renderers.
- `worker/`: the headless entry (`index.ts`), its `Dockerfile`, `docker-compose.yml` (worker + Postgres) and `clem-worker.service` (systemd + Node). `scripts/build-worker.mjs` bundles it (`npm run worker:build`; the desktop build puts a copy in `desktop-dist/worker`).
- `core/vps/`, `desktop/engine/vps/`, `src/vps/`: the VPS connector (see VPS below).

## Data
- **Databases:**
  - Desktop: PGlite (`@electric-sql/pglite`, moved to `dependencies`), stored under `Documents/Clem/Accounts/<owner>/engine/`.
  - VPS: real Postgres in Docker.
  - Both are behind the same `Db` interface: `query(sql, params)` and `tx(fn)`.
- **Migrations:** SQL files in `desktop/engine/migrations/NNN_*.sql`, applied in order and recorded in `engine_migrations`.
- **Scoping:** every table has `owner_id`, and every query filters on it. The AI only ever sees the current owner's rows.
- **Tables:**
  - GUC data: `guc_courses`, `guc_schedule_slots`, `guc_announcements` (with `read_at`, and `position`, the post's place on its course page, migration 013), `guc_materials`, `guc_grades`, `guc_deadlines`.
  - `guc_snapshots`: one row per sync, holding the per-page content hash, ETag and Last-Modified.
  - `guc_events`: `new_grade`, `new_announcement`, `new_material`, `deadline_added`, `deadline_changed`, `schedule_changed`.
  - `subject_links`: subject id ↔ GUC course.
  - `subject_settings`: save rules, schedule and Drive settings as JSON.
  - `file_objects`: location `device|vps|drive`, sha256, size, pinned, `last_access`.
  - `notifications_sent`: unique on `(owner_id, event_key, channel)`.
  - `jobs`: if the job runner needs its own table.
  - `telegram_link`; `migration_state` (per file: item, direction, status, attempts) and `migration_runs` (migration 007); `engine_lease` (the worker's single-runner lease).
- **Credentials:**
  - GUC password and SSH key go in the Vault (desktop) or an encrypted file using AES-256-GCM (worker).
  - They are never written to workspace state, logs or prompts, and never put in error messages.

## GUC
- **Auth:** NTLM through `httpntlm`, with one keep-alive agent per owner.
  - Try the username both as given and with a `GUC\` prefix.
  - Detect the IIS 401 page as a credentials failure.
  - TLS checking stays on. If GUC's certificate chain is broken, pin or add the missing intermediate rather than disabling checks.
- **CMS** (`https://cms.guc.edu.eg/apps/student/`):
  - `HomePageStn.aspx`: the course grid (see "What is read" below).
  - `ViewAllCourseStn`: list of all courses.
  - `CourseViewStn.aspx?id=&sid=`: one course. Files are in `.card-body` blocks, week headings in `h2` ("Week: YYYY-MM-DD"), and downloads in `a#download`. The course description is `#ContentPlaceHolderright_ContentPlaceHoldercontent_desc` and weekly announcements are in `div.weeksdata`.
  - This layout is ported from AhmedAshrafAZ/cms-downloader (MIT); credit it in THIRD-PARTY-NOTICES.
- **Portal** (`https://apps.guc.edu.eg/student_ext/`):
  - `Scheduling/GroupSchedule.aspx`: the schedule.
  - `Grade/Transcript_001.aspx`: grades. It needs a postback on the year dropdown.
  - "Page will be available from…" means skip this time, not an error.
- **Deadlines:** pulled out of announcements and course content. The main thread's model reads new posts with the person's own classes (`core/guc/deadline-ai.ts`); with no model, the rule reader does (`core/guc/deadlines.ts`, chrono-node plus keywords such as "deadline", "due" and "submission"). Rules both follow (user, 2026-11-13, after a list of sentence-long titles and wrong dates):
  - A title is what is due ("Quiz 2", "In-class assignment 3", "Submit your solutions"), never the sentence. The sentence is the note.
  - Only a written date counts: "now", "today" and "tomorrow" are not dates, since when a post was written isn't known.
  - A date with no year is the one closest to today and at most a term (150 days) ahead; "10/5" in November is not next May's deadline.
  - A weekday that isn't the date's ("Tuesday November 18th" on a Wednesday) is a slip in the post, not old text: the earlier of the two days is kept and the note says which two, so nothing is missed.
  - "During the second tutorial of the week starting Saturday 7 November" is the person's own second tutorial that week, at its start time, when their schedule is known; otherwise the week's first day.
  - `DEADLINE_VERSION` is bumped when reading changes: course pages are read again and what the new reader finds is a baseline, not news.
  - **What is read** (user, 2026-11-14: only one deadline was tracked although posts and mail held five). Both readers get the student's own classes for the course (now that classes belong to their courses, below) and their short groups (`shortGroup` in core/guc/codes.ts: "3MIET T014" → T14, "L002" → L2, "P014" → P14). Each item has `kind` (quiz, exam, assignment, in-class, lab, project, presentation, other), `place`, `covers`, `timeKnown`, and `either` when it is sat on one of several days by group and theirs isn't known ("Monday or Tuesday, by tutorial group"; `due` is then the earliest day). A table row naming their group ("T13 - T17", "T11,T12,T14" include T14; `groupIn`) gives that row's day, time and room. "The first tutorial of the week starting …", "the tutorial starting the next week (14/11-19/11)" are their own tutorial that week, with its room; "the last 40 minutes" of a 90-minute slot starts 50 minutes in. A post's date stamp ("[4/11/2026]:") is when it was written, not a date in it.
  - **Course mail is read too**: a new mail `mailAbout` places under one of the student's courses keeps 2,000 characters of its body (`GucMail.text`, course mail only; the Mail tab shows the preview) and is a text for that course's reader (`mailTexts`: "Email: " + the subject without "[EXTERNAL EMAIL] -", "Notification System:" and the "[Group: …]" tag). Mail to everybody never is. One item from a post and a mail is one item: the rule reader's ids are the item's name, and `applyReader` matches by kind and number (`itemKey`: "CSEN 301 quiz #2" is "quiz|2").
  - **Seating plans and schedules uploaded as files** (user, 2026-11-14: "sometimes a file is uploaded on CMS with seating plan"): the one kind of CMS file Clem reads on its own; every other file is only listed. In the sync's second step, a material new since its course's last read (never on a course's first read, a reader's re-read or a `DEADLINE_VERSION` baseline) whose title or file name `isSeatingFile` accepts (seating, seats, seat plan, room/hall distribution or allocation, quiz/midterm/final/exam/in-class schedule, rooms or locations; never solutions, samples, slides, sheets, revision) is fetched once through the client (GUC hosts only, not links or videos, HEAD first and at most 8 MB, `FILES_PER_SYNC` 3 a sync), its text extracted in memory (file-text.ts) and never stored or marked saved. `fileText` keeps its first ~1,500 characters and the lines naming the student's groups, sign-in name or student id (about 4,000 in all); it is one more text for the course's reader (source "file", label "File: <title> (<week>)"). The model is told to update the matching tracked item's place and time from it, adding an item only when the file clearly announces one not tracked. The rule reader (`fileUpdate`) sets the room (and the row's time near that day) of the item the file's title names ("Quiz 2 seating plan" → Quiz 2), from the one row naming their group; unsure which item or row: nothing. Such an item's source is "file" and its note says which file. A room given or changed at the same time is one `deadline_changed` event, "CSEN 701 Quiz 2: now in Exam Hall 4", keyed `dl:<id>:place:<hash>` so it is told once. Read files are remembered in `seen.files.read` (last 500); a failure is skipped quietly and tried on the next syncs, `FILE_TRIES` 3 times in all.
  - **The model** is asked with those groups, the portal's exam seats for the course (so a midterm isn't added twice), 6,000 characters a text and 24,000 in all; a long table keeps its header and the rows naming their groups first (`fitText`).
  - **Deadlines are the sync's second step** (guc-sync.ts): announcements, files, grades, mail and their events are saved first (progress "saved" refreshes the window), then each course whose page was read, or that has a new course mail, has its unread texts read, at most `READERS_AT_ONCE` (2) model calls at a time, `READER_MS` (60 s) each, and the deadlines, their events and the snapshot are updated in a second transaction. A model that doesn't answer leaves the rules' answer and the texts unread, `READER_TRIES` (3) times for the same texts (`seen.deadlines.fails`); then the rules' answer stands until the texts change.
  - **Event titles** are a clean phrase: "MATH 301 Quiz 2: Tuesday 17 Nov at 16:30, Exam Hall 4"; "ELCT 301 Assignment 2: due Thursday 19 Nov"; "… (Monday or Tuesday, by tutorial group)".
  - `DEADLINE_VERSION` is 5 for all of this: everything is read again by the new readers as a silent baseline.
- **Incremental sync:**
  - Send conditional requests (ETag / If-Modified-Since). Otherwise compare a content hash per page, and skip parsing when it is unchanged.
  - Only fetch courses that are linked to a subject, plus the light course list.
  - Requests are batched, at most 2 at a time per host, with exponential backoff on errors.
- **Errors:** sync failures are typed (`auth`, `site_changed`, `offline`, `unavailable`). The user gets one friendly notice, deduplicated, never repeated.

## What is read, and how often (user, 2026-11-13)
The layouts follow what the working Grok bot read (guc-cms-scrapper 0.2.5 and its check_portal.py / check_mail.py):
- **CMS course list:** `HomePageStn.aspx`, table `…_GridViewcourses`: the label "(|CODE|) NAME (ID)" in the second cell, the season id in the sixth. The older season-header layout still reads. A course list Clem can't read keeps the last one and the rest of GUC is still read (then the sync reports `site_changed` once).
- **Course pages:** each `.card-body`: title = first child of `[id^=content]`, kind = the text after it, file = the first link. An absolute href (Google Drive) is kept as is; "/Uploads/…" never gets a double slash. Week dates may be unpadded.
- **Announcements are whole posts** (user, 2026-11-14: "it's supposed to be one message, not separated"). The course's announcement box used to be split at every paragraph and table cell (one course became ~80 "announcements" such as "T6,T7,T8,T9"). `core/guc/parse.ts`:
  - `readPieces` reads the box as written: block elements are paragraphs, `<br>` a line (two, a paragraph), list items "- item", a link its text plus "(url)" when the text isn't the address, and a table one line per row with cells joined by " · ", rowspan and colspan spread so each row is complete ("Monday 16.11 · 3:45 P.M. · T29 - T30 · D1.003"), a colspan cell said once, the header row first. A cell's own lines are joined with a space; nested tables are read inside their cell; a table of one cell per row is a frame and its cells read as paragraphs.
  - `announcementPosts` splits only at clear boundaries: an `<hr>`, a line of five or more `-`, `_`, `=` or `*` (dropped), or a paragraph opening with a date stamp ("[4/11/2026]: …" wherever a line starts; "4/11/2026:" and "(4/11/2026)" where a paragraph starts). The stamp stays in its post and the tables after it belong to it. Greetings, sign-offs and tables stay inside their post; a box with no boundary is one post; a post with no letter or digit is dropped.
  - Each post has `order` (0 at the top; week announcements follow the box's posts) and an id hashing course, scope and text. A week's announcement (`div.weeksdata`) is still one, read by the same reader (`boxText`), so its table or list survives.
  - **An edited post is an update** (`announcementEdits` in core/guc/diff.ts): a new post sharing at least 0.6 of the shorter one's lines with one that went away in the same read (same course, scope and week) is one `new_announcement` event, title "Updated announcement in CODE", its new or changed lines first. Only spacing or punctuation changed: no event, and the row keeps the old one's first-seen and read state; otherwise it is first seen now and unread. Event detail is the whole post up to 1500 characters, newlines kept.
  - **`ANNOUNCEMENT_VERSION`** (parse.ts, now 2) is to announcements what `DEADLINE_VERSION` is to deadlines: `seen.announcements = { v, courses }`. A course not read by this version has its page read again once (memo ignored) and its posts are a baseline: no announcement events, and no deadline events either (diff.ts counts a course as read by the same deadline reader only when the same announcement reader read it too, because the texts' ids changed). The deadline reader reads every one of that course's posts again (its "texts already read" are ignored once) so it still finds deadlines; the course counts as switched only once that read worked, so an AI that didn't answer leaves the next read a baseline too. Read state carries over in `save` (`inherited` in guc-sync.ts): a course with nothing unread before the switch has every post read; otherwise a post is unread only if it holds the text of an old unread row; a post is first seen when the earliest old row inside it was (else now). Compared on letters and digits only, with link addresses taken out. A course read for the first time is new and unread as before.
- **This term's grades:** `Grade/CheckGrade_01.aspx`: midterms (`…_midDg`), then one postback per course on `…_smCrsLst` with every named input copied from the latest page (view state goes stale), coursework in `…_nttTr`.
- **Exam seats:** `Exam/ViewExamSeat_01.aspx`: the first table whose header says "Exam Day" or "Exam Type".
- **Portal bounce:** a short page calling `sTo('…')` is retried with `?v=<token>`.
- **Browser headers and cookies (checked live 2026-11-13):** the portal answers HTTP 500 to any request without a browser User-Agent, so every request sends one, and each sync keeps the session cookies it is given (the bounce token belongs to that session). The CMS grid's columns are Name, Active, Season ("Winter 2026"), ID, SeasonId: the course link takes SeasonId (or the row's own link), never the year in Season.
- **Transcript, a study year at a time:** GUC loads the transcript at most once a minute (a second load shows "temporarily paused", read as unavailable) and shows one study year per load. Each sync posts back one year (`nextTranscriptYear`): unread past years newest first, until a past year with no grades (before the student started; GUC still shows such years empty semester tables), then whichever of this year and last year was read longer ago. While past years are unread the part stays due, so pulses two minutes apart fill them in. A year read for the first time is a baseline, not new grades.
- **VPS worker updates:** a worker installed by another app version is refreshed with this version's bundle when the desktop starts its heartbeat (`VpsManager.refreshWorker`); its database is kept.
- **Mail:** EWS at `mail.guc.edu.eg/EWS/Exchange.asmx`, read-only by construction except one write (core/guc/ews.ts: `ewsRequest` builds only GetFolder/FindItem/GetItem and refuses any other operation; `markReadRequest` is the one UpdateItem, setting only `message:IsRead` to true on one item, `SaveOnly`, `AlwaysOverwrite`, with the change key FindItem returns, never stored). New = EWS ids not seen before (kept only as hashes); bodies only for new ids, 300 characters. The first read is a baseline. A mail failure never pauses the rest of GUC.
- **TLS stays on everywhere.** Node trusts the Sectigo chain all three hosts serve.
- **A mail opened in the hub is read** (user, 2026-11-14: "when I view email it's actually read"). The hub's `gucMailMessage` calls `Engine.mailMessage(id)`, which by default marks it read: `readMessage(…, { markRead: true })` sends the UpdateItem when Exchange still says unread (a refusal is ignored; the message still opens), and `markMailOpened` (guc-read.ts) marks its row in the latest snapshot and adds its hash to `seen.mailRead` (last 500). `read.mail` and each sync OR that set into `read` (the sync also takes in opens recorded while it ran), so it stays read whatever Exchange or the next sync says. The AI's `guc.mail` passes `{ markRead: false }`: reading for the person never marks anything. The window patches the list and the Mail count at once; the note under the list says opening marks it read and that Clem never sends, moves or deletes mail.
- **Who a mail is for** (`core/guc/mail-about.ts`): FindItem also asks for `item:DisplayTo` (the names a message was written to; a server that refuses it is asked again without). With the course codes in the subject and preview and the sign-in name, each new mail is the student's course's (`courseKey` on its `new_mail` event), written to them alone, or sent to everyone (event key `mail:all:…`). Only the first two are ever told (docs/MAIN-THREAD.md → "Only what is true and yours"); all of it is in the Mail tab.
- **Classes belong to their courses** (user, 2026-11-14): the portal's schedule cell names the course ("Mathematics III", "Physics III (t)"), so `parseSchedule` stored the name as the code and nothing matched a class to its course. Each sync resolves every slot's `code` from the course list (`slotCourse` in core/guc/match.ts: a code in the cell; the same name with case, spacing, punctuation, "&"/"and" and roman numerals aside; the name without its bracket, where "(t)"/"(p)" picks PHYST or PHYSP by the code's last letter; else `rank` only when sure; the newest active term). An unmatched slot keeps what it has; `name` stays as the portal wrote it; slot ids are the portal's and don't change. `scheduleHash` reads the name, not the code, so resolving is never "your schedule changed".
- **Mail paging:** the Inbox is listed newest first and a pulse stops after a page holding only ids it has seen (one request when nothing is new); every page is listed on the first read and once a day (`lastRead.mailFull`). Opening a message lists newest first until the page that holds it.
- **Course pages:** two at a time per host (the client's limit); a page slower than `PAGE_MS` (45 s) is left for the next pulse, and a page that failed (`seen.retry`) is read on the next pulse whatever its pace. No connection or a wrong password still stops the sync before anything is saved, so a retry tells nothing twice.
- **Pace (guc-sync.ts PACE):** a pulse every 2 minutes reads only what is due: mail 3 min, linked course pages 5, CheckGrade 15, exam seats 30, course list 60, schedule 180, transcript 360; four times slower 01:00–07:00 Cairo. A quiet pulse updates the latest snapshot in place instead of adding a row. "Sync now" and connecting read everything.
- **Routines** (core/proactivity/routines.ts) with a `change` trigger run straight after the sync that found the news, not at the next sweep.

## Password expiry (user, 2026-11-12)
GUC can force a password change every 30 days. When sign-in fails with an `auth` error:
- **Retry once,** after a short delay to rule out a blip.
- **Mark the connection `password_needed`.** Pause all GUC checks for that owner without wiping any data or settings, so nothing hammers GUC and the account can't get locked out.
- **Tell the user once** through the notifier at urgent level, on every channel they enabled (including Telegram), deduplicated by key `guc-auth:<date of first failure>`: "GUC isn't accepting your password. If the uni asked you to change it, enter the new one here." Show it as a card in the main thread with **Update password**.
- **Update password** opens Settings → Connectors → GUC on an inline "New password" field. It is NOT a disconnect.
- **On save:** verify the new password, store it in the Vault, clear the flag, resume the jobs, and run a catch-up check.
- **Hub and subject pages** show the same banner.
- **Reminders:** at most one gentle reminder per day while the flag is still set, and none during quiet hours.
- **How it is built** (`core/guc/password.ts`, tested in `tests/guc-password.test.ts`):
  - The flag is `guc_account.password_needed` (migration 006): when it first failed.
  - **Only the CMS home page refusing the saved password sets it** (user, 2026-11-13: "keeps saying to update password while there isn't"). After any `auth` error the engine waits `AUTH_RETRY_MS` (8 s) and asks the home page once with a fresh client. Refused: flagged. Accepted: the sync runs once more, and a page that still refuses (the portal, one course, a file) is recorded as that page being unavailable, never as a password problem.
  - **Why false alarms happened:** NTLM signs in a connection, not a request, and `httpntlm` sends its two messages through the agent it is given. On one agent shared by requests running side by side, the second message could leave on another request's socket, and GUC answered 401. `ntlmHttp` now gives every exchange a one-socket agent of its own.
  - **A flag clears by itself when it was wrong:** `Engine.recheckPassword` asks the home page once with the saved password 25 s after the engine starts and every `PASSWORD_RECHECK_MS` (6 h) while flagged. If GUC takes it, the flag clears, the jobs come back and a catch-up runs, with nothing for the person to do. One request every six hours can't lock an account.
  - Pausing unschedules `guc.sync` and every `guc.check` schedule; while flagged, `reschedule` adds none, the job handlers return, and every path to GUC (sync, checks, viewing or reading a CMS file) throws the friendly auth error without a request. Resuming schedules `guc.sync` again and rebuilds each linked subject's checks from its settings as they are now. The catch-up is a sync, then each linked subject's check with trigger `rules`.
  - The notice is `Organizer.gucPassword()`, called when it fails and on every `organizer.tick`: the `guc_password` card (live: once it works, it says so) posted once under `guc-auth:<Cairo day>`, and a push under the same key on every outward channel turned on for any event (urgent, so the level doesn't hold it; quiet hours queue its pushes). Later days push `guc-auth-reminder:<day>` outside quiet hours, with no new card.
  - Update password is the route `#/app/connectors/guc`: Settings → Connectors with the GUC dialog, which shows the "New password" field while flagged (`gucPassword` IPC → `Engine.updatePassword`). Telegram's card button opens the same route in Clem.

## Jobs
- **Runner:** pg-boss, running on PGlite on the desktop and on Postgres on the VPS.
  - **Decision (step 1, proven):** pg-boss 12 runs on PGlite 0.5 through its own `fromPglite` adapter (`backend: "pglite"`, schema `pgboss`). The spike and `tests/guc-jobs.test.ts` show a failed job retried with backoff, and jobs and cron schedules (with `tz`) surviving a close and reopen. So there is no `jobs` table and no croner (check schedules use pg-boss cron too; see Check schedules). The wrapper is `desktop/engine/jobs.ts`.
  - Each owner has their own database, so queue names leave the owner out (`guc.sync`, not `guc.sync:<owner>`). Per-subject checks are `guc.check` schedules keyed by subject and cron line.
  - `guc.sync` runs every three hours (`0 */3 * * *`, Cairo time) while GUC is connected. A wrong password is not retried. Offline and unavailable errors retry 3 times with backoff from 2 minutes.
- **Bundling:** `scripts/build-desktop.mjs` maps `import.meta.url` to the bundle's own file URL, copies `pglite.wasm`, `pglite.data` and `initdb.wasm` beside `main.cjs`, and copies `desktop/engine/migrations` to `desktop-dist/migrations`. `pg-native` stays external.
- **Job names:**
  - `guc.check:<owner>:<subjectId>`: one per subject, from its schedule rules.
  - `guc.sync:<owner>`
  - `organizer.sweep` (keys `morning`, `midday`, `evening`, `weekly`, Cairo time; event sweeps are sent with a singleton key) and `organizer.tick` every 10 minutes (deadline reminders, quiet-hours pushes). See docs/MAIN-THREAD.md "Proactivity".
- **Timezone:** Africa/Cairo by default.

## Chat cards
- Assistant messages carry ` ```clem-card ` fenced blocks with a JSON body, checked against a zod schema in `core/guc/cards.ts`.
- `MessageBody.tsx` renders them the same way it renders ` ```plan `.
- Card types: `course_link`, `save_rules`, `check_schedule`, `drive_folder`, `storage`, `file_saved`, `announcement`, `grade`, `deadline`.
- When a card is edited, the outcome is written back to the engine through IPC, and the card shows live state read from the engine, not a frozen copy.

## UI rules
- Use only existing components and tokens: `SettingsCard`, `SettingRow`, `Switch`, `EmptyState`, `PageHead`, `Icon`, `confirmDialog` and `Toast`, plus the glass tokens and the scale in `src/glass/glass.css`.
- No new UI library. `@tanstack/react-virtual` (headless) handles long lists.
- Data shows instantly from cache, then refreshes in the background. Edits update the screen immediately. Loading states use skeletons, never a blank screen.
- Respect the existing memory rules: text sits small inside its button, the logo never animates, and never fade a parent of glass.

## GUC hub
- **Reads** (`desktop/engine/guc-read.ts`, owner-scoped): `gucOverview`, `gucCourses`, `gucSchedule(weekStart)`, `gucAnnouncements({courseId?, cursor})` (40 a page, newest first-seen first, then page position, then id; the cursor is "<ms>.<position>.<id>", an older "<ms>.<id>" reads as position 0), `gucMarkRead(ids)`, `gucMaterials(courseId)` grouped by week, `gucSearch(query)` (ILIKE over file names and announcements, every word must match), `gucGrades({courseId?})`, `gucDeadlines` (Coming up, below).
- **Files:** `gucFile(materialId)` and `clem://app/api/local/guc/file/<id>` serve the saved copy (`file_objects`, `guc:<id>`) or fetch the file on demand through the NTLM client into a temp folder (`EngineHost.paths.temp`, else the system temp). Temp copies go when the engine closes or GUC disconnects; what save rules keep is served from its saved copy (see Checks and saved files). The window reads them as `guc_<id>` through `getBlob`, so the existing viewer (PDF, slides, images) shows them read-only.
- **Shared logic** (`core/guc/hub.ts`, tested): result types, the Sat–Thu week in Africa/Cairo, deadline order and relative times, semester order, and the `#/app/guc/<tab>/<id>/<sub>` routes (`schedule`, `announcements/<id>`, `cms/<course>/<file>`, `grades`, `deadlines/<id>`) for notifications to link to.

## Subject setup
- **Course codes** have one form everywhere, "CSEN 701" (`core/guc/codes.ts`): the parsers write it, the engine's reads rewrite older rows, and comparisons go through `codeKey`.
- **Matching** (`core/guc/match.ts`): an exact code wins; otherwise name words (prefixes, plurals, small typos, roman numerals, initials) plus fuse.js. `sure` (≥ 0.75 and 0.12 ahead of the next) is what lets Clem ask "This looks like CSEN 701 — link it?"; otherwise it offers the alternatives.
- **Links** (`desktop/engine/subjects.ts`, migration `002`): one course per subject and one subject per course (linking moves it). Linking runs a light sync of that course only (`Engine.syncCourse`, queued behind any full sync). Each linked subject's checks are `guc.check` pg-boss schedules keyed `<subject>/HHMM` (pg-boss keys allow no colon), from its check rules; Check now is the same light sync. Deleting a subject forgets its link and settings.
- **Settings** live in `subject_settings` as JSON (`core/guc/settings.ts`): save rules, check schedule (default: 30 min after each of the course's lectures, else Sat–Thu 20:00, Africa/Cairo), Drive and storage, and the setup state. Patches are zod-checked; the window applies them optimistically (`src/guc/subject.ts`) and the engine's answer replaces the guess.
- **Ask once, never per subject** (user, 2026-11-13: "ask what the user wants and set it up, no pop-ups, no same questions asked again"). Setup asks one thing, and only when Clem can't tell: which CMS course a subject is. What to keep, when to check, the Drive copy and storage are never asked per subject.
  - What Clem keeps is one answer for all courses: the settings row `ALL_SUBJECTS` ("_all"), set in chat ("keep everything from all my courses") through `guc.settings` with `"everywhere": true` or a `settings_update` block with `everywhere`. `Engine.setSettings(ALL_SUBJECTS, …)` saves it and applies it to every linked subject; a subject with no settings of its own starts from it (`subjects.defaults`; before it exists, from the last answer an older setup got, else the built-in default). One subject can still differ. Clem's first hello (`Organizer.offerSetup`) is where it is asked, once.
  - A new subject opens its own page, not a chat. Behind it `begin(id, { quiet: true })` (`linkQuietly` in `src/guc/setup.ts`) links the course when the match is sure and says so in a toast. Nothing else happens: no Setup chat is made and nothing is posted (user, 2026-11-13: no automated setup messages). When it isn't sure, nothing is asked; the subject stays unlinked and its CMS tab offers the likeliest courses.
  - The subject's Settings tab shows what is kept and the Drive copy; where files live only once a VPS is connected. There is no check schedule to set (Clem looks every few minutes); Check now is on the course bar.
- **Setup thread** (`core/guc/setup-flow.ts`, `src/guc/setup.ts`): exists only when the person taps "Set up in a chat" on a subject's CMS tab. A pure state machine decides the next question (only `link` applies now); the typed reply is read locally, and by the AI only when the local parser can't. Clem never makes, opens or writes to a Setup chat by itself. Setup chats older versions made stay where they are; nothing new is posted into them.
- **Rules converters**: `convertSaveRules` and `convertCheckSchedule` (below) read typed replies; `parseSaveRules`/`parseCheckSchedule` remain as their local-only wrappers.
- **Cards** read live state through one `gucSubject` read per subject (never a frozen copy): `course_link`, `save_rules`, `check_schedule`, `drive_folder` (shell: toggle, open, change folder via the subject's Drive link; copying arrives with Drive sync), `storage` (device only until a VPS is connected), `setup_done`, `settings_update`, `new_courses`. The subject page's CMS tab shows the same cards. Settings → Connectors → GUC lists no subjects (since 0.3.34): it signs in, syncs and disconnects, and each subject's settings live in its own chat and page.

Nothing to pick. No new tool or IPC path.

## Save rules
- **Shape** (`core/guc/rules.ts`): the kinds of CMS file (slides, assignments, tutorials and sheets, videos, links, other) plus optional filters every kept file must also pass: file types (`only`/`except`, from the link's extension), week numbers (`from`/`to`, counted from the course's oldest week on CMS by the date in its heading), name globs (`*`, `?`, case-insensitive, against the title and the file name) and `maxMB`. Defaults: slides, assignments, sheets and other files; no filters.
- **Words → rules**: `convertSaveRules(text, current)` reads "all lecture slides", "only PDFs", "everything except videos", "nothing, I'll open on demand", "slides and sheets under 50MB", "only week 3 onwards", "files named Lab*". A new statement of what to keep ("only slides") starts clean; a change ("stop saving videos", "also videos", "under 20MB") keeps what it doesn't mention. Leftover words it doesn't know, contradictions ("only slides except slides"), "files over 50MB" alone and "skip week 3" (a hole a range can't hold) are `{ needsAI: true }`.
- **The AI** answers with JSON that must pass `aiSaveRules` (strict zod: known kinds and types only, weeks 1–60 with from ≤ to, globs without slashes, positive sizes; `null` removes a filter). The same schema checks every settings patch.
- **`matches(rules, material, { week, size })`** is the only gate before a download. A size rule passes until the size is known; the check asks with a HEAD first.
- **Described** for cards: "Everything · PDFs only · week 3 onwards · under 50 MB"; "Nothing (open files on demand)".

## Check schedules
- **Shape** (`core/guc/schedule-rules.ts`): fixed times (day + "HH:MM"), an optional repeat (`every` minutes between two times on some days) and an optional date range (`during`), always on Cairo's clock (Africa/Cairo, daylight saving included).
- **GUC week**: Saturday to Thursday. "Weekdays", "school days" mean Sat–Thu, and descriptions say "Sat–Thu (GUC week)"; "weekend" is Friday.
- **Words → schedule**: `convertCheckSchedule(text, { suggested, slots, code, exam })` reads "every 2 hours on weekdays 8am–10pm", "twice a day", "only on lecture days" (the course's lecture days at 20:00), "hourly during exams" (the 21 days up to the subject's exam date), "after each lecture". It answers `{ ask }` when only the person knows (no exam date, no lectures on the schedule) and `{ needsAI: true }` for the rest ("every day except Friday").
- **Never more often than every 30 minutes**, whatever is asked (shared server, battery, data).
- **Default**: 30 minutes after each of the course's lectures plus one 21:00 check those days; a course with no classes gets Sat–Thu at 20:00.
- **Cron**: `cronLines` groups the week's times by minute and days ("0 8,10,12 * * 0,1,2,3,4,6") with a stable key per line. pg-boss runs them with `tz: Africa/Cairo`; no croner. `nextRuns(n)` lists what is coming and is tested against pg-boss's own cron parser, across the April and October clock changes.
- **Date ranges** can't be cron: the job wakes up and does nothing outside them.

## Checks and saved files
- **Jobs**: each linked subject's lines are `guc.check` schedules keyed `<subject>/<line key>`. A settings change reconciles: lines whose cron changed or went away are removed, new ones added, the rest left alone.
- **A check** (`Engine.check`, one per subject at a time): the course page conditionally (ETag/If-None-Match, else the content hash) → diff → events; then `saveFiles` (`desktop/engine/check.ts`): only materials the rules keep, on a GUC host, not links, and not saved yet or whose link changed; two downloads at a time (the client's per-host limit), stored one at a time. An unchanged page with everything saved costs one request and no downloads. "Check now" runs one; new save rules run one without the page after the taps settle (15 s), but not mid-setup before the save question is answered. Linking only reads the page.
- **Storage** (`desktop/engine/storage.ts`): `FileStore`; `DeviceStore` keeps bytes under `Documents/Clem/Accounts/<owner>/Files/GUC/<sha256>.<ext>`, written once per hash. The same bytes from another CMS entry reuse that file. Each saved file is shown in the workspace as `Files/guc_<material>.blob`, a hard link to the same bytes (a copy only on file systems without hard links), so the viewer, backups and the AI's working folder read it like any file. Replaced bytes nobody uses any more are deleted. A VPS store comes later behind the same interface.
- **Records**: `file_objects` (migration `003`) gains material, subject, link, name, type and the Drive copy's id, hash, folder and root. `guc_checks` keeps one row per check (trigger, page changed, requests, bytes, saved, skipped, deduped, uploaded, ms, error; last 200 per subject) for the performance pass. A file a size rule refused after download is remembered (`notifications_sent`, channel `too_big`) and not fetched again.
- **To the window**: the engine has no workspace state, so saves are `file_saved` events and the window pulls them through `gucInbox`, acknowledged with `gucAckInbox` (channel `thread`). The window only adds the saved files to their subject's Files; it writes nothing into any chat. News (announcements, grades, deadlines, saved files) is said once, by the organizer in the main thread (docs/MAIN-THREAD.md → "Only what is true and yours").

## Drive copy
- `desktop/engine/drive-mirror.ts` copies a subject's saved files to `Clem/GUC/<code name>/<week>` in My Drive, or into week folders under a folder the person chose (the existing DrivePicker). Folders are found or made once and cached (`drive_folders`).
- A file is sent once per root folder and content (`drive_sha256`); the same bytes already in that week folder reuse that Drive file; an unchanged file is never sent again. A new folder sends the files there; the old copies stay.
- Drive goes through the host (`EngineHost.drive`). On the desktop that is DriveLive with two additions: `folderIn(parent, name)` and an optional type for `uploadFile` (default unchanged). Nothing else in Drive changed.
- Drive not connected (or a token that can't write) records `reconnect` in `subject_drive`, and the card shows Reconnect Drive (Settings → Connectors); files wait and go on the next check or toggle.
- **Card**: the toggle, the folder in use, copied and waiting counts, Open, Change folder, Use Clem/GUC.

## AI tools
- **Actions**: GUC joins the one `kinetra` tool as namespaced actions (`core/guc/ai-tools.ts` `GUC_ACTIONS`, added to `ACTIONS` in `desktop/kinetra-turn.ts`), so every CLI reaches them the same way, natively over MCP or as `{"kinetra":…}` text: `guc.schedule(range, subject?)`, `guc.deadlines(range?, subject?)`, `guc.announcements(subject?, since?, unread?)`, `guc.materials(subject)`, `guc.read(file, from?)`, `guc.grades(subject?)`, `guc.search(query, subject?)`, `guc.settings(subject, saveText/checkText/rules/save/check/drive)` and `guc.help`. The spec's names (`get_schedule`, `read_file`, `update_subject_settings`…) read as aliases. Reads are QUICK (they run in parallel); `guc.settings` is not.
- **Guide and skill**: `GUC_GUIDE` (one line per action, byte-stable) is the `guc` playbook in `core/clem-skills.ts`, chosen only when GUC is connected and the chat is a subject's or the message is about study (schedule, deadlines, slides, grades…). Nothing is added otherwise, so other prompts keep their cache.
- **Where they run**: `desktop/main.ts`'s chat `tools` handles `guc.*` first, in the main thread and in subject chats alike, with `runGucTool` (`desktop/engine/ai-tools.ts`). A subject chat (`scope` `subject:<id>`) makes that subject the default.
- **Owner**: the engine is per owner and `runGucTool` refuses an engine that isn't the signed-in owner's; every read goes through the owner-scoped engine reads. Subject names and exam dates come from the window's state (the engine has only ids).
- **Subjects** resolve (`resolveSubject`) by linked subject id or `@id`, a course key or code ("csen702"), a subject's exact name, then fuzzy names of linked subjects and courses (`core/guc/match.ts`); close calls answer "could be A or B: say which".
- **Output**: compact text, capped (40 deadlines or grades, 80 files, 25 search hits, 15 announcements by default), each line with its `#/app/guc/…` link so the AI cites it; the rest is summarized as "…and N more (hint)". Ranges are Cairo days; the schedule spans at most 14 days.
- **guc.read**: any CMS file by id (or a title, the subject's first), saved or not. Bytes come from the store that holds the file (`file_objects.location` → a `FileStore`, which gained `read`; only `device` today, a VPS or Drive store plugs in by location, and one this host can't reach falls back to CMS), else the viewer's temp copy, else straight from CMS through the NTLM client into memory: nothing is written, nothing is recorded as saved. Text: PDFs with pdfjs-dist's legacy build in Node (its worker on the main thread via `globalThis.pdfjsWorker`, so the bundle needs no worker file), PowerPoint, Word and Excel through `desktop/office-text.ts` (`officeBytesText`, the same reader the working folder uses), text as is (`desktop/engine/file-text.ts`). Parts per page, slide or sheet (Word in ~4k-character parts), returned about 24k characters at a time with `[name, page N]` markers and a "continues at page N" request. The text stays in an `lru-cache` (45 min since last read, 12M characters, 200 files) per engine, so reading on costs no download; disconnecting or closing clears it.
- **guc.settings** builds a `settings_update` card from the request and runs it through `updatePatch` (the converters for the person's words, `aiSaveRules`/`checkSchema` for structured fields), checks the patch with `settingsPatch`, then calls `Engine.setSettings` like a card; what the converters can't read comes back as an error with the structured format. Only for subjects linked to a course; no unlink or check-now from the AI here (the `settings_update` block still has them).
- **Now card**: `Engine.now()` (IPC `gucNow`) gives today's classes, deadlines in the next 7 days and the unread count (`gucNow`), cached under a version bumped by every sync, check, mark-read and disconnect, and by the Cairo hour. The window merges it into the local card (`withGuc` in `core/main-thread/context.ts`) for each main-thread turn.
- **Checks**: `tests/guc-ai-tools.test.ts` (each tool on the fixture GUC, resolution, owner scoping, saved vs unsaved reads with cache hit and TTL, PDF and PPTX extraction from `tests/fixtures/guc/lecture.pdf` and `deck.pptx` made by `scripts/make-guc-text-fixtures.mjs`, settings validation, the Now card, and a tool call over the MCP endpoint as a CLI makes it).

## VPS (built 2026-11-11)
"It's as if Clem is running on the VPS": files and background work live there, always on; the desktop is the window and a cache.

- **Connection** (`desktop/engine/vps/link.ts`, `keys.ts`): ssh2 + ssh2-sftp-client behind a `VpsLink` (exec with an output cap, SFTP, a local port tunnelled to the worker). Keys are ed25519 made in the app (`ssh2.utils.generateKeyPairSync`) or pasted; the private key (and passphrase) live only in the Vault record `vps-<owner>`; the window gets the public line and the one-liner `mkdir -p ~/.ssh … >> ~/.ssh/authorized_keys`. Password sign-in is off unless the Advanced toggle is on. Host keys are trusted on first use: the first test shows and stores the `SHA256:` fingerprint; a different one is refused with a plain message (forget the server to reset). Errors are sentences, never stack traces.
- **Settings → Connectors → VPS** (`src/vps/VpsSettings.tsx`, `desktop/engine/vps/manager.ts`): server → key → Save and test (latency, OS, free disk, Docker, systemd, Node). Connected: a status dot, Test connection, where files live (usage on this PC vs the VPS, Move everything / Move back with progress and Stop, the cache limit, pinned files), Background jobs, a model key for the VPS, what is sent, Forget this server (only once files are back).
- **Storage** (`desktop/engine/vps/store.ts`, `router.ts`): `VpsStore` keeps bytes at `~/clem/<owner>/files/<sha256>.<ext>`; an upload goes to a `.part-*` name, the server's own `sha256sum` must match before it takes its name, and reads are hashed again. Main puts a `StorageRouter` in front of every workspace file (`blobs` in `desktop/main.ts`: `/api/local/files/<id>`, uploads, attachments, generated files, specs, versions; the window's API is unchanged) once a VPS is set up. Metadata is `file_objects` `ws:<id>` (location, path, sha256, size, pinned, cached). Writes always land in `Files/<id>.blob` first; in VPS mode they go to the VPS too and the row says so only after the check; a failed upload leaves the file on this PC for the next move. This PC keeps an `lru-cache` of VPS files (default 2 GB, `vpsCap`; size-calculated; files bigger than the cap aren't kept), and pinned files (`vpsPin`) are outside it. Files only on this PC are never evicted. Prefetch (`core/vps/prefetch.ts`): opening a file brings the same space's files from the same week; a chat turn brings the files its messages refer to, and the AI's working folder fetches a VPS-only file only when its copy there is missing. Saved CMS files follow the host's `fileStore()` (the VPS store in VPS mode); a CMS file the worker saved reaches the window through the worker's engine (`fileBytes`) and is then kept like any file.
- **Moving files** (`desktop/engine/vps/migrate.ts`): Move everything (up) / Move back (down), one file at a time, each in `migration_state`. Workspace files and saved CMS files (`guc:*`). A file's row points at its new place only after that copy is checked; the source is freed only then (up: the device copy becomes cache and the LRU trims it; down: the VPS copy is removed once nothing uses it). A checksum failure is retried, then marked failed with its source untouched (the run ends `failed`: "N files couldn't be moved. They are safe on …"). A lost connection pauses (`paused`); `resumeMove` carries on after a restart. Stop (abort) leaves moved files where they were checked and the rest where they are, so every row points at a copy that exists. Writes during a move go to the new place (the mode switches when it starts). Done posts a `vps_moved` card in the main thread (once).
- **Background worker** (`worker/index.ts`): the same `Engine`, headless. Docker when the user can run `docker compose` (worker + `postgres:16-alpine`, the worker's port published on `127.0.0.1` only, run as the VPS user's uid), else a systemd user unit with Node 22+ and PGlite under `state/`. `installWorker` (`desktop/engine/vps/install.ts`) uploads `desktop-dist/worker`, writes `config.json`, `.env` (mode 600), the key file and the sealed secrets, then starts it; turning it off stops it. After install, subject links and settings and the organizer's settings are copied to the worker's empty database (`handover`). The desktop pushes the compact workspace snapshot (`snapshotOf`, sent with `__snapshot`) on every workspace save (at most every 20 s); the organizer's posts and actions come back through the same `proInbox`, because the window's engine requests go to the worker.
- **Reaching the worker:** a small HTTP endpoint on `127.0.0.1:7717` (`rpc.ts`), reached only through the SSH tunnel, every request with the RPC token (constant-time compare). `/rpc` calls only `RPC_METHODS` (the engine's reads and actions the window uses); `/workspace`, `/lease`, `/health`, `/notices` (the worker's notices, shown as this PC's notifications). In main, `engineFor` wraps the engine: while the worker runs jobs, those methods go to it; `file` comes back as bytes. GUC connect and a new password are checked here first (and kept in the Vault), then sent to the worker.
- **Single runner** (`core/vps/lease.ts`): one lease in the worker's database (`engine_lease`). The worker beats every minute and runs jobs while it holds it; the desktop steps it through `/lease` on its own beat. A desktop holding it hands it back as soon as it sees the worker; it takes over only when the worker's heartbeat is older than 10 minutes (or it can't reach the worker for that long). `Engine.runner(on)` starts or stops pg-boss, the organizer's queue and the Telegram inbox. Two engines can only both run while the desktop and the VPS can't see each other at all; jobs are keyed (notifications per key per channel), so a repeat is the worst case.
- **What goes to the VPS, and how** (`WORKER_SECRETS`, shown in Settings): the GUC username and password (`guc-<owner>`), a Telegram relay token (`engine-token`: minted by `POST /engine/token` on the account Worker, stored there as a SHA-256 hash, one per account, accepted only on `/telegram/*` with `Authorization: Engine …`; not the Clem session), a model API key only if the person typed one for the worker (`model`), and the RPC token (`rpc`). Each is sealed with AES-256-GCM under a 32-byte worker key made at install (bound to its name), sent over SFTP, and stored as `state/secrets/<hash>.enc` (mode 600); the key file is `.key` (mode 600, not in the Docker image: mounted read-only). Root on the VPS can read them; that is the trust the person gives their own server. Nothing is logged. The SSH key and Drive tokens are never sent.
- **Model on the VPS** (`headless.ts`): Clem never stores or copies provider API keys (Settings → Models signs in with the person's own CLI), so the worker uses, in order: an Anthropic API key typed for the worker (`claude-opus-5-5` by default, low effort), a `claude` (`claude -p`) or `codex` (`codex exec -`) CLI the person installed and signed in to on the server themselves, else none: sweeps run on rules alone and ambiguous items wait for the desktop.
- **Telegram on the VPS:** with a model, the worker answers Telegram itself (`headlessConverse`: the Now card, GUC and Telegram tools in the `{"kinetra":…}` text form, at most four calls). Without one, the worker leaves the Telegram inbox to the desktop, which answers as before while the worker runs everything else. Buttons that need the window (Summarize, Undo in the window) say so.
- **AI tools** (`core/vps/tools.ts`, `desktop/engine/vps/tools.ts`; the `vps` playbook, only while a VPS is connected and the message is about it): `vps.service_status`, `vps.read_file` (200 KB), `vps.write_file` (new files at once; an overwrite asks), `vps.run_command` (output capped at 8000 characters). `classifyCommand` is conservative: a command runs at once only if every part is a known read-only command used read-only; redirects into files, substitution, sudo, unknown words and destructive flags get a `vps_confirm` card (Run it / Cancel, kept 15 minutes in main, run once, owner-checked).
- **Setup thread:** the storage step asks only with a VPS; with "Store my files on my VPS" on, it says files will be stored there, and the storage card shows how many are on the VPS and on this device.
- **Known gaps:** Drive copies of files kept on the VPS wait (the Drive mirror reads device paths); the worker doesn't run Drive. The worker's database starts from the handover copy, not the desktop's history (it syncs GUC itself). Pending `vps_confirm` actions don't survive a restart. Disabling the worker leaves its files and database on the server.
